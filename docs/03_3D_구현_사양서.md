- **하드코딩 금지.** 색·간격·모션은 `tokens.css` 변수를 읽어 쓴다. three.js 머티리얼도 예외 없음(§4-3).

## 1. 개념 — 이 화면이 말하는 한 문장

> **"문장이 아래에서 위로 올라가는 동안 의미가 재배치되고, 어느 층에서 답이 굳는다."**

3D가 정당화되려면 **2D로는 못 하는 일**을 해야 한다. 이 설계에서 3D만 할 수 있는 것은 정확히 셋이다.

| # | 3D 전용 표현 | 대응 요구 | 2D에서 불가능한 이유 |
|---|---|---|---|
| **①** | **세로 궤적** — 토큰 하나가 24~64개 층을 지나며 의미 축에서 어디로 이동하는지가 **하나의 연속된 선** | 00 §5-1 | 2D는 층을 한 번에 하나씩만 볼 수 있다(슬라이더). 전체 경로가 동시에 안 보인다 |
| **②** | **결정 깊이의 높이** — 답이 굳는 지점이 **공간상의 높이**로 보인다. 모델 간 비교(24층 vs 64층)가 실루엣으로 즉시 | 00 §5-2 | 2D의 "L18/24"는 숫자다. 숫자는 비교하려면 읽어야 한다 |
| **③** | **의미의 수렴/발산** — 층이 올라가며 토큰들이 Z축에서 모이는지 흩어지는지 | 00 §5-3 | 2D 산점도는 한 층만 |

**따라서 attention 엣지는 3D의 주인공이 아니다.** 엣지는 초점 층 1개만 그리고(E-2), 3D의 세로 방향은 궤적과 결정 깊이가 독점한다. 이 판단이 이 사양서 전체의 뼈대다.

### 1-1. 벤치마크에서 가져올 것 / 가져오지 않을 것

Transformer Explainer는 **한 화면 다이어그램 + 아래 읽을거리** 구조이고, 라이트 단일 배경에 클릭-확장 인터랙션을 쓴다.

**가져온다** — 무대 + 읽을거리 2단 구성(C안), 스테이지 라벨 고정, 호버=경로 추적, 클릭=제자리 확장, 반복 블록을 접어 압축.
**가져오지 않는다** — cyan 팔레트, 2D 평면 한정 구도, 영문 전용 타이포 스케일.

## 2. 좌표계

### 2-1. 축 정의 (E-1)

```
        Y (층)
        ↑  L23 ─────────── 최상단, 여기서 답이 나온다
        │  L22
        │   ⋮
        │  L0
        │  Emb ─────────── 바닥
        └──────────────→ X (토큰 순서, 문장 읽는 방향)
       ╱
      Z (의미 축 = PC1, 앞뒤)
```

| 축 | 의미 | 성격 |
|---|---|---|
| **X** | 토큰 순서 `i ∈ [0, T)` | **고정 격자.** 데이터에 따라 움직이지 않는다 |
| **Y** | 층 `l ∈ [0, L]` (`l=0`은 Embedding) | 고정 격자 |
| **Z** | 의미 축 = 층별 hidden state의 PC1 | **유일한 데이터 구동 좌표** |

**정면 카메라(−Z 방향으로 바라봄)에서는 X–Y 평면만 보이므로 2D 흐름도와 같은 구도가 된다.** 이것이 평면 모드 전환의 시각적 연속성을 만든다(§5-2, §11).

### 2-2. 스케일 상수

> **v1.1 수정.** 구 공식 `DY = clamp(0.35, 14/L, 1.2)`는 `L=64`에서 하한 0.35에 걸려 총 높이가 22.4가 되었다 — "총 높이 14"를 달성하지 못하는 버그였다. 아래로 교체한다.

> **v1.8 수정 (2026-08-27 디자인 감사).** 구 사양의 `DX = 1.0` 고정은 **세로만 억제하고 가로는 놔둔 것**이라, 토큰이 많아질수록 상자가 옆으로 길어졌다. v1.7에서 정면 종횡비(X:Y)를 `ASPECT_TARGET`에 맞추는 억제를 넣었으나, **Z는 `ZMAX` 고정폭이라 X:Z는 그대로 벌어졌다** — 59토큰 실측 **10.7 : 1**, 측면 뷰가 "얇은 판자"로 보였다(§15-4 판정 2·3 불합격). 이제 DX는 **정면 기준·측면 기준 두 후보 중 더 좁은 쪽**이다. 정면은 목표에 "맞는" 것이 아니라 그 **이하**가 된다 — 정면의 여백은 값싸고 측면의 붕괴는 비싸다.

```js
const H0 = 14.0;                             // 기준 총 높이 (L=24 기준)
const H  = H0 * Math.sqrt(L / 24);           // 총 높이 — 층 수의 제곱근에 비례
const DY = H / L;                            // 층 간격
const ZMAX = 2.6;                            // 의미 축 최대 진폭 (±)

const ASPECT_TARGET   = 1.7;                 // 정면 목표 종횡비 (X:Y) — 무대 종횡비
const Z_ASPECT_TARGET = 2.2;                 // 측면 상한 종횡비 (X:Z) — v1.8 신설
const DX_MAX = 1.0, DX_MIN = 0.15;           // 짧은 문장은 DX_MAX, 하한은 씬 수축 방지용

// 토큰 간격 — **T에 따라 정해진다. 상수가 아니다.**
const DX = clamp(Math.min(
  (ASPECT_TARGET   * H)        / (T - 1),    // ① 정면(X:Y)을 무대에 맞춤
  (Z_ASPECT_TARGET * 2 * ZMAX) / (T - 1),    // ② 측면(X:Z)이 판자가 되지 않게
), DX_MIN, DX_MAX);

const NODE_R = 0.26 * DX;                    // 노드 반지름 (간격에 비례 — 좁아져도 안 겹친다)
const NODE_H = 0.55 * NODE_R;                // 원반 두께 (v1.8: 0.28 → 0.55)

x(i) = (i - (T - 1) / 2) * DX
y(l) = l * DY
z(l, i) = clamp(pc1n[l][i], -1, 1) * ZMAX    // pc1n = §2-3에서 정규화된 값
```

| L | H (총 높이) | DY | 24층 대비 높이비 |
|---|---|---|---|
| 24 (0.5B) | 14.00 | 0.583 | 1.00 |
| 40 (14B) | 18.07 | 0.452 | 1.29 |
| 64 (32B) | 22.86 | 0.357 | 1.63 |

**DX 실측 (v1.8 규칙 적용 후)** — `tools/test_coords.mjs`가 이 표를 회귀로 지킨다.

| 장면 | L | T | DX | 정면 X:Y | 측면 X:Z |
|---|---|---|---|---|---|
| 단문 | 24 | 7 | 1.000 | 0.43 : 1 | 1.15 : 1 |
| 한국어 문장 | 24 | 59 | 0.197 | 0.82 : 1 | **2.20 : 1** (구 규칙 10.7 : 1) |
| 14B | 40 | 59 | 0.197 | 0.63 : 1 | 2.20 : 1 |
| 32B 최악 | 64 | 96 | 0.150 (하한) | 0.62 : 1 | 2.74 : 1 |

- 짧은 문장은 두 후보 모두 `DX_MAX`를 넘으므로 **예전과 똑같이 1.0**이다 — 잘 보이던 장면을 건드리지 않는다.
- 96토큰에서는 `DX_MIN`에 걸려 측면 목표(2.2)를 약간 넘는다. 하한은 씬이 한 점으로 수축해 카메라가 near 평면에 닿는 것을 막는 안전장치라 우선한다.
- 정면이 `ASPECT_TARGET`(1.7)보다 **작아지는 것은 의도**다. 카메라는 `fitDistance`가 상자를 보고 거리를 잡으므로, 상자가 세로로 길면 세로 기준으로 맞춰져 **층 간격 픽셀이 오히려 늘어난다.**

**왜 제곱근인가 — §15-4 판정 5와의 모순 해소**

구 사양은 §2-2에서 "높이가 비슷해야 모델 비교가 성립"이라 하고 §15-4 판정 5에서 "모델을 바꾸면 실루엣이 눈에 띄게 달라야" 한다고 요구했다. **두 요구는 서로 반대 방향이었다.** 정리하면:

- **선형(`DY` 고정)**이면 64층이 24층의 2.7배 높이 → 화면에 담으려 카메라가 멀어져 노드가 뭉갠다. 게다가 "높다"는 사실은 층 수를 세면 알 수 있는 것이라 정보가 없다.
- **완전 정규화(총 높이 고정)**면 실루엣이 똑같아져 비교할 게 없어진다.
- **제곱근**이면 층 수 4배에 높이 1.6배. 화면에 담기면서 실루엣 차이도 남는다.

그리고 **"실루엣 차이"의 근거를 높이 하나에 걸지 않는다.** §15-4 판정 5가 보려는 차이는 셋이다:
① 총 높이(1.0 : 1.29 : 1.63) ② **결정 깊이의 상대 위치**(0.5B는 마지막 층, 14B는 중간에서 확정 — 이게 진짜 차이) ③ 의미 축 퍼짐의 층별 패턴. 두 모델을 나란히 놓았을 때 ②가 가장 크게 다르다.

### 2-3. PC1 기저 안정화 · 정규화 — **가장 중요한 데이터 규칙**

`hidden_proj`를 **층마다 따로 PCA**하면 층 사이에서 축의 의미가 달라져 **궤적이 전부 거짓말이 된다.** 아래를 반드시 지킨다.

| 규칙 | 내용 |
|---|---|
| **전역 기저** | PCA는 `(L+1) × T` 개의 hidden state **전체를 한 행렬로 쌓아 한 번만** 적합한다. 층별 적합 금지 |
| **부호 고정** | PC1의 부호는 임의다. `Emb 층의 첫 토큰 z ≥ 0`이 되도록 전체 부호를 뒤집어 고정. 같은 프롬프트를 재분석했을 때 그림이 앞뒤로 뒤집히면 안 된다 |
| **시점 정렬 (v1.3 기본값)** | **PCA 적합 전에 모든 층을 같은 시점으로 맞춘다** — 중간 층에는 `final_norm`을 적용하고 마지막 층은 그대로 둔다(이미 적용돼 있으므로). `engine.logit_lens.proj()`와 **같은 코드 경로를 공유한다**. 정규화(L2·층별 z-score)는 적용하지 않는다 |
| **결정론 (v1.3 필수)** | `torch.pca_lowrank`는 **무작위 SVD**다. `torch.manual_seed(고정값)` + `niter ≥ 12`. 이걸 빠뜨리면 같은 프롬프트를 재분석할 때마다 축이 바뀐다 — 부호 고정으로는 못 막는다(부호가 아니라 축 자체가 바뀐다) |
| 스케일 | `PC1_SCALE = percentile(|pc1|, 98)` — 전체(층·토큰 통합) 기준. `pc1n = pc1 / PC1_SCALE` |
| 과잉 고지 | `overflow = max|pc1| / PC1_SCALE`. **5를 넘으면** 이상치가 스케일을 지배하는 중이므로 캡션에 `일부 값이 표시 범위를 크게 넘습니다` 1줄 + 콘솔 경고 |
| ~~하위 파이프라인 확인~~ | **확인 완료(v1.3).** `all_but_the_top`은 전역 적합이다(`H.reshape(L1*seq, d)` 후 1회 호출, 내부 `mean(0)`도 전 층 통합). 전역 기저 규칙이 지켜지고 있다 |

#### 2-3-1. 시점 정렬이 기본값 — 재현 가능한 실측으로 확정 (v1.3)

> **v1.1·v1.2의 결론은 무효다.** 두 번 모두 **재현되지 않는 측정** 위에서 내린 판단이었다. 아래는 결정론을 확보한 뒤 다시 잰 결과다.

**먼저 잡아야 했던 것 — 측정이 재현되지 않았다**

`torch.pca_lowrank`는 무작위 스케치를 쓰는 근사 SVD인데 시드가 없었다. 같은 입력·같은 방식에서:

```
run1  l2  squashed = 16%   통과
run2  l2  squashed = 32%   눌림    ← 판정이 갈린다
run3  l2  squashed =  8%   통과
```

**이건 프로브만의 문제가 아니다.** 백엔드 `panels.py::_hidden_projection`이 같은 함수를 쓰므로, **같은 프롬프트를 재분석할 때마다 투영이 달라진다.** R3-05("재분석 시 그림이 뒤집히지 않을 것")는 부호 고정만으로는 지켜지지 않는다 — 부호가 아니라 **축 자체가 바뀐다.** 현행 2D의 ⑤ 공간 패널도 이미 이 상태다(산점도라 눈에 덜 띄었을 뿐이다).

`torch.manual_seed()` + `niter=12`로 완전 재현을 확인했다(run1 = run2 완전 일치).

**재측정 결과 (Qwen2.5-0.5B · 7토큰 / 36토큰)**

|---|---|---|---|---|---|
| linear | 88% ✗ | 80% ✗ | 0.61 | 20% | 탈락 |
| l2 (v1.2 기본값) | ~~76% ✗~~ | 8% ✓ | 0.63 | 7% | **탈락** (근거는 아래 v1.6) |
| per_layer | 88% ✗ | 92% ✗ | **0.97 ⚠** | 16% | 탈락 (단일 차원 대리변수) |
| **postnorm — 시점 정렬** | **4% ✓** | **4% ✓** | 0.65 | 8% | **채택** |
| postnorm + l2 | 4% ✓ | 40% ✗ | 0.73 | 8% | 탈락 |

- **v1.6 정정: "L2가 짧은 프롬프트에서 76%로 무너진다"는 철회한다.** 시드 없던 시절 관측이라 재현되지 않는다. **L2 탈락의 근거는 `proxy`로 바뀐다** — 32B 짧은 조건에서 L2는 `0.91`로 **단일 차원 대리변수 판정**(R3-06b 기준 0.9 초과)이고 postnorm은 `0.75`다. 결론(postnorm 채택)은 그대로지만 이유가 다르므로 여기 적어둔다.
- **두 방식을 겹치면 오히려 나빠진다**(postnorm+l2 = 40%). 하나만 고른다.
- `per_layer`의 `proxy 0.97`은 R3-06b 검증이 실제로 작동함을 보여준다 — PC1이 특정 hidden 차원의 대리변수가 된 경우를 정확히 잡아냈다.

**대형 모델 확인 (v1.6, T3-0b 완료)**

판정 행 p98 · 합격선 `squashed ≤ 20%` · 전 모델 **2회 실행 완전 일치**.

| 모델 | 층 | 짧음(8토큰) | 김(94토큰) |
|---|---|---|---|
| 0.5B | 25 | 16% ✓ | 4% ✓ |
| 1.5B | 29 | 3% ✓ | **38% ✗** |
| 14B | 49 | 6% ✓ | 8% ✓ |
| 32B | 65 | **20% ✓(경계)** | 17% ✓ |

- `linear`는 8조건 전부 미달(69~92%). **시점 정렬의 필요성은 모델을 키울수록 뚜렷해진다.**
- **경계·이탈 사례가 실재한다** — 32B 짧은 조건이 정확히 20%(p99로는 22%), 1.5B 긴 조건이 홀로 38%. 앞뒤 모델이 통과하므로 크기 추세는 아니고 원인 미규명이다.
- **따라서 QA 시점의 확인만으로는 부족하다.** 사용자는 HF repo id를 임의로 입력할 수 있으므로(01 문서 F-31) 카탈로그 밖 모델이 언제든 들어온다. **런타임 가드가 필요하다** — §2-3-2 참조.

**원인 — 마지막 층만 다른 시점이었다**

`hidden_states[-1]`은 이미 `final_norm`이 적용된 상태다. 실측:

```
마지막 층 :  head(h) vs logits 오차 = 0.0000    ← 그대로가 정답 (post-norm)
중간 층 L11:  head(h) 5.96  /  head(norm(h)) 5.32   ← norm이 필요 (pre-norm)
층별 ‖h‖ 뒤 3개 :  75.4 → 84.2 → 369.8   (마지막이 직전의 4.39배)
```

**마지막 층 하나만 다른 지점에서 찍힌 값이었고, 그 인위적인 4.39배 점프가 퍼센타일 스케일을 독점해 나머지를 전부 눌렀다.** norm 성장도(v1.1) massive activation도(v1.2) 주범이 아니다.

**이 진단이 이전 둘보다 신뢰할 만한 이유:** 앞의 둘은 "무엇을 나누면 그림이 나아지는가"라는 사후 관찰이었고, 이번 것은 **`head(h)` 오차라는 독립적인 증거**로 확인됐다. 마지막 층은 norm 없이 logits를 정확히 재현하고 중간 층은 아니다 — 시점이 다르다는 직접 증거다.

**그래서 정규화가 아니라 버그 수정이다**

시점 정렬은 "보기 좋게 만드는 변환"이 아니라 **서로 다른 것을 비교하고 있던 것을 고치는 일**이다. 그리고 이 로직은 **이미 제품 안에 있다** — `engine.logit_lens.proj()`가 중간 층엔 norm을 적용하고 마지막 층은 생략한다. `_hidden_projection`만 그걸 안 하고 있었다.

> **원칙으로 남긴다: 한 제품 안에서 같은 것을 두 가지 방식으로 계산하지 않는다.**
> 고치는 방법은 새 로직을 쓰는 게 아니라 `logit_lens.proj()`와 **코드 경로를 공유하는 것**이다.

**부수 효과 두 가지**

1. Z축이 logit-lens가 읽는 것과 **같은 공간**에 놓인다. "이 층이 지금 답한다면 뭐라고 할까"와 "이 토큰이 의미 축에서 어디 있나"가 같은 좌표계에서 일어나므로, 궤적과 층별 예측이 서로를 설명한다.
2. 2D ⑤ 공간 패널과 3D Z축이 같은 정의를 쓰게 되어 **모드 전환 시 그림이 일치**한다.

**v1.2의 "의미 = 방향" 논증은 어떻게 되나**

원칙으로는 여전히 옳지만, **잘못된 진단을 덮는 데 쓰이고 있었다.** 데이터 버그를 고치고 나면 정규화가 필요 없고, 오히려 L2를 덧씌우면 실제 신호가 깎인다(긴 프롬프트 40%). 크기 정보는 시점 정렬 후에는 층 간 비교 가능한 값이 되므로 버릴 이유가 없다.

#### 2-3-2. 진단 지표 (v1.3)

**게이트는 `squashed` 하나다.**

```
squashed = (층별 median|z_norm| < 0.20 인 층의 수) / (L+1)      # 게이트: ≤ 20%
overflow = max|pc1| / PC1_SCALE                                 # 참고: > 5 면 경고
```

**폐기 — 클립률(v1.2)은 tautology였다.** 스케일을 p퍼센타일로 잡으면 클립률은 **정의상 정확히 (100−p)%**다. "클립률 ≤ 2%가 되는 가장 낮은 퍼센타일"은 계산할 필요도 없이 항상 p98이고, 방식을 전혀 가르지 못한다. 대신 `overflow`(가장 큰 값이 표시 범위의 몇 배인가)를 본다 — 이건 이상치 지배 여부를 실제로 말해준다.

> **폐기된 지표를 두 번 만들었다. 원리로 남긴다.**
> `R`(v1.1) — 중앙값 기반 지표로 퍼센타일 기반 스케일을 진단했다. 꼬리에 둔감했다.
> `clip`(v1.2) — 스케일 정의에서 기계적으로 따라 나오는 값을 독립 지표로 착각했다.
> **새 지표를 만들 때는 "이 지표가 방식 A와 B를 실제로 다르게 판정하는가"를 먼저 확인한다.**

**런타임 가드 (v1.6 신설) — 진단은 QA용이 아니라 제품 기능이다**

`squashed`는 개발 중에만 재는 값이 아니다. **분석마다 계산해 응답에 실어 보내고, 임계를 넘으면 화면에 알린다.**

| 조건 | 화면 동작 |
|---|---|
| `squashed ≤ 20%` | 평소대로 |
| `squashed > 20%` | 의미 축 캡션 옆에 `--warn` 1줄: `이 모델·문장에서는 앞뒤 축이 잘 퍼지지 않습니다 — 의미 이동을 과소평가할 수 있습니다.` |
| `overflow > 5` | 별도 1줄(기존 규칙) |

- 근거: **카탈로그 밖 모델을 사용자가 직접 넣을 수 있다.** 1.5B 긴 프롬프트(38%)·32B 짧은 프롬프트(20% 경계)가 실제로 존재하는 이상, "QA에서 통과했으니 괜찮다"는 성립하지 않는다.
- 이건 성능 저하가 아니라 **정직성 요구**다 — 축이 정보를 못 담고 있는데 아무 말도 없으면 사용자가 "이 모델은 의미 변화가 없다"고 잘못 읽는다.
- 필드는 `hidden_proj.squashed: float`(B-01d).

**PC1 정체 검증 (유지)**

| 검사 | 기준 | 실측 |
|---|---|---|
| `max_d \|corr(PC1, h[:,d])\|` | < 0.9 | postnorm 0.65 — 통과. per_layer 0.97 — 탈락 |
| PC1 설명 분산(evr) | **상시 병기** | 전 방식 7~20%. 조건부 규칙이 항상 참이라 조건을 없앤다 |

**evr이 낮은 것을 숨기지 않는다.** 캡션은 항상 `의미 축 (PC1 · 분산 8%)` 형식으로 쓰고, `이 화면 읽는 법`(§12-1)에 한 문장을 더한다 — *"앞뒤 축은 수백 개 숫자를 한 줄로 눌러 담은 것이라 전체의 일부만 담습니다."* 축 하나가 의미의 전부인 척하지 않는다.

#### 2-3-3. 재현성 게이트 (v1.3 신설) — **사양을 바꾸는 모든 측정에 적용**

v1.1과 v1.2의 결론이 연달아 뒤집힌 원인은 판단력이 아니라 **재현되지 않는 측정을 근거로 썼다는 것**이다. 같은 일이 성능 측정·페이로드 측정에서도 일어날 수 있다.

| 규칙 | 내용 |
|---|---|
| **2회 일치** | 사양을 바꾸는 측정은 **동일 조건으로 2회 실행해 결과가 완전히 일치**해야 채택한다. 불일치하면 결론이 아니라 **비결정성의 원인부터 찾는다** |
| **산출물 존재 검사 (v1.6)** | **비교 전에 두 산출물이 비어 있지 않은지 먼저 확인한다.** 빈 스트림 둘을 `diff`하면 "일치"가 나온다 — 실측에서 이 게이트가 **실패를 통과로 둔갑시킨 사례**가 나왔다. 최소 크기와 필수 키를 검사한 뒤에 비교한다 |
| 시드 고정 | 난수를 쓰는 모든 경로(`pca_lowrank`, 샘플링, 초기화)에 고정 시드. 시드값은 측정 기록에 함께 남긴다 |
| 조건 기록 | 모델·프롬프트·토큰 수·라이브러리 버전·시드를 결과 파일 상단에 |
| **단일 관측 금지** | 프롬프트 1개, 실행 1회로 사양을 바꾸지 않는다. **최소 2프롬프트 × 2회** |
| 반대 증거 | 새 결론이 이전 결론을 뒤집으면, 이전 결론이 왜 나왔는지도 함께 기록한다 |

**백엔드 절감:** 의미 축이 1개뿐이므로 `hidden_proj`를 q=3으로 확장할 필요가 없다. 기존 q=2의 PC1만 쓴다.

### 2-4. 보조 모드 — 의미 지도 (P2, 선택)

"토큰 순서를 버리고 의미만 보는" 모드. `X = PC2`, `Z = PC1`, `Y = 층` 유지. 원안(02 문서)의 구도가 필요할 때를 위한 탈출구로 남긴다. **기본값 아님**, 하단 컨트롤의 토글. 이 모드에서는 attention 엣지를 자동으로 끈다(읽을 수 없으므로).

### 3-3. 세로 궤적 (3D 전용 표현 ①)

> **v1.5 — A/B 확정: 궤적 = `TubeGeometry`(월드 단위).** 단계 1 실측에서 p99 차이가 pr1 −0.10ms / pr2 −0.50ms로 판정 기준(3ms) 안이었고, 16배 부하(삼각형 11.8M)에서도 120fps가 유지됐다. 깊이 단서를 얻는 쪽을 택한다.
> 엣지는 attention 가중치를 굵기로 인코딩하므로 줌에 따라 변하면 안 된다 → **화면 단위 `LineSegments2`**(§4-5). 굵기 4단계 유지도 실측으로 확인됐다(draw call 84에서도 영향 없음).

- 토큰 `i`의 `(x(i), y(l), z(l,i))` `l=0..L` 을 잇는 폴리라인. **CatmullRom 보간 8분할**로 부드럽게(꺾인 선은 노이즈처럼 보인다).
- 기본: **관 반지름 = 0.10 × DX**(지름이 노드 지름의 40%), 색 `--ink-4`를 `--paper` 쪽으로 혼합해 **알파 0.42** 상당.
- 선택 토큰: 반지름 2.6배, 색 `--ink`, 알파 1.0. 나머지는 알파 0.08로 후퇴.

> **v1.8 수정 (2026-08-27 디자인 감사).** 구 사양의 "폭 1.0px · 알파 0.22"는 화면 단위 선을 전제한 표현이라 월드 단위 관으로 역산하면 `0.062 × DX`(지름 ≈1.2px)였는데, **7토큰짜리 가장 쉬운 장면에서조차 보이지 않았다.** 1.2px는 이론상 지오메트리 지름이지 실제로 덮이는 픽셀 수가 아니다 — 안티에일리어싱과 원근(월드 단위라 멀수록 얇아짐)이 겹치면 서브픽셀로 사라진다. "선"이 아니라 "가는 리본"으로 보일 굵기라야 실측에서 살아남는다.
- **마지막 토큰(답을 만드는 자리)의 궤적은 결정 깊이 위 구간만 `--signal`.** 아래 구간은 `--ink`. 이 색이 바뀌는 지점이 §3-6의 "굳는 순간"이다.

**병합 규칙 (v1.5 — 근거 정정)**

> **v1.4의 근거는 틀렸다.** "개별 Mesh 96개 → 첫 프레임 51.6초"와 "머티리얼 96개 → 셰이더 96회 컴파일"은 **둘 다 사실이 아니었다.** 51.6초는 hidden 탭에서 첫 `rAF` 콜백이 51.5초 뒤에 온 것이고, 머티리얼을 96개로 나눠도 three.js가 캐시 키(타입+defines)로 공유하므로 **셰이더 프로그램은 1개**다. 지오메트리 생성도 세 변형 모두 61~79ms로 같다.

| 항목 | 실측 |
|---|---|
| 병합 · 머티리얼 공유 | 지오메트리 79ms · compile 2ms · **draw call 1** · 프로그램 1 |
| Mesh 96 · 머티리얼 공유 | 61ms · 2ms · draw call 96 · 프로그램 1 |
| Mesh 96 · 머티리얼 96 | 74ms · 1ms · draw call 96 · **프로그램 1** |

**병합의 유일한 근거는 draw call 96 → 1이다.** 빌드 시간은 오히려 +18ms 손해다. 그리고 개발 머신(M4 Max)에서는 draw call 84에서도 120fps라 **성능 이득이 관측되지 않았다.**

그럼에도 **병합을 채택한다** — 근거는 성능이 아니라 아래 셋이다.

1. **저사양 보험.** 발표 노트북 측정 전이며, 내장 GPU에서는 draw call 96과 1의 차이가 드러날 수 있다.
2. **선택 강조 애니메이션.** 단일 배치 + 정점 색이면 색 보간을 속성 갱신 한 번으로 처리한다.
3. 궤적에는 피킹을 하지 않으므로(§7-2는 노드만) 병합의 통상적 단점이 없다.

- **선택 강조는 정점 색(vertex color) 부분 갱신**으로 한다. 궤적별 정점 구간의 시작·끝 인덱스를 미리 저장하고, 선택이 바뀌면 그 구간의 색 속성만 `needsUpdate`.
- **개별 `Mesh` 96개도 금지는 아니다.** v1.4의 "하드 규칙"은 철회한다 — 근거가 무너진 규칙을 남기지 않는다. 다만 기본 구현은 병합으로 간다.

### 3-4. attention 엣지 (초점 층만)

- 층 `l`의 평면 위에서 query `q` → key `k` 아치. **평면에서 아래로 살짝 처지게** 그려 노드와 겹치지 않게 한다.

```js
// v1.1: 아치의 부풀림을 DY에서 분리한다.
// 구 사양(mid.y -= 0.42*DY)은 층 간격이 좁아지면(64층 DY=0.357) 아치가 납작해져
// 곡선이 층 평면에 파묻히고 인접 층 노드와 겹쳤다. 주 부풀림을 Z(뒤쪽)로 옮긴다.
const p0 = V(x(q), y(l), z(l,q));
const p1 = V(x(k), y(l), z(l,k));
const span = Math.abs(x(q) - x(k)) / DX;           // 몇 토큰 건너뛰는가
const mid = p0.clone().lerp(p1, 0.5);
// v1.8: 부풀림 기준을 DX → ZMAX로 바꾼다. DX에 비례시키면 토큰이 많아 DX가 눌릴수록
// (= 아치가 서로 겹치기 딱 좋은 순간) 오히려 더 납작해진다. 59토큰·엣지 574개 실측에서
// 초점 층 바로 위에 "검은 낙서"로 뭉쳤다. ZMAX는 토큰 수와 무관한 고정 깊이 예산이다.
mid.z -= ZMAX * (0.11 + 0.035 * Math.min(span, 4));  // 주 부풀림 = Z, ZMAX 기준
mid.y -= Math.min(0.18 * DX, 0.45 * DY);             // 보조 처짐 = Y, DY 상한
curve = new THREE.QuadraticBezierCurve3(p0, mid, p1);  // 16분할
```

- 멀리 건너뛰는 엣지일수록 더 뒤로 부풀어 겹침이 줄어든다.
- Y 처짐은 `0.45 * DY`를 넘지 않으므로 **층 간격과 무관하게 아래층을 침범하지 않는다.**

- 굵기: `0.6 + w * 3.2` **픽셀**(화면 공간). 확대해도 굵기가 값 그대로 유지된다.
- `w` 정규화·sink 처리는 **[2D스펙] §5-2-1 / §5-3을 그대로 계승**한다:
  - `w = clip(a[q][k] / maxNonSink[q], 0, 1)`
  - `sinkMass ≥ 0.5`인 query의 `k=0` 엣지는 **점선**(`dashed`, dashSize 0.14, gapSize 0.10), 굵기 1.5px 고정, 색 `--ink-4`
  - 프루닝: query당 상위 12개, `w < 0.02` 생략, **생략 개수를 콘솔·`<details>`에 기록**(조용한 절삭 금지 — 01 문서 D-02)
- 색: `--ink`를 `--paper` 쪽으로 `alpha = 0.10 + w*0.80` 만큼 혼합(§4-5 이유).
- 호버한 토큰이 query면 그 엣지만 `--ink` 불투명, 나머지 0.08.

### 3-5. 층 평면 · 바닥 · 축

- 초점 층: `PlaneGeometry`를 XZ에 눕혀 `--ink` **알파 0.025**로 채우고 테두리 1px `--line-strong`. 크기 = 노드 바운딩 + 0.6 여백.
  - **v1.8 수정.** 0.04라도 무대 가로·깊이 전체를 덮는 큰 면이라, 3/4 시점에서 여러 겹이 겹쳐 보이며 화면 위쪽이 뿌옇게 흐려졌다("안개"). 결정선과의 대비만 지키면 되므로 더 죽인다.
- 초점 ±1층: 테두리만 `--line`, 채움 없음.
- 나머지 층: **아무것도 그리지 않는다.** 64개 평면은 시각 소음이다.
- 바닥 그리드: Emb 층 아래 `0.8 * DY`에 X방향 선 T개 + Z방향 선 5개, `--line`. `GridHelper` 사용 금지(기본 색·분할이 규격 밖).
- 3D 안에 축 라벨을 그리지 않는다 — 층 눈금은 DOM 레일(§9-3)이, 토큰 라벨은 DOM 오버레이(§6)가 담당.

### 3-6. 결정 깊이 (3D 전용 표현 ②)

- 결정 깊이 층 `y(d)`에 **수평 기준선** 1개: X 범위 전체 + Z 범위 전체를 두르는 사각 윤곽, 색 `--signal`, 굵기 1.5px.
- 그 층부터 위로 **마지막 토큰 위치의 노드가 `--signal`로 굳는다.**
- DOM 라벨(리더선 포함): `L18에서 답이 정해집니다` — `--signal-ink`.
- **기준선 색은 `--signal`을 `--paper` 쪽으로 40% 섞은 값**(채도 0.6)을 쓴다. 순정 `--signal`이 아니다.
  - **v1.8 수정.** 초점 층은 기본값이 결정 깊이라(§7) **흔한 초기 상태에서 결정선과 초점 테두리가 같은 y에 겹쳐 그려진다.** 게다가 토큰 라벨은 그 y 바로 위에 뜨는데, 결정 깊이가 최상단 근처면 위로 뺄 여유가 없어 순정 보라 테두리가 라벨 줄과 부딪힌다(실측: 라벨이 테두리 위에 얹혀 보임). 라벨 위치는 건드리지 않고 **선 자체를 죽여서** 해결한다 — §3-5의 "눈에 띄면 실패다"와 같은 원칙. 등장 페이드인(0→1 opacity)은 그대로 둔다.
- **결정 깊이가 없을 때**(마지막 층에서야 확정): 기준선을 그리지 않고, 최상단에 `--warn` 좌측 세로선 + `답이 마지막 층에서야 정해졌습니다` 1줄. **[2D스펙] §6-3-2 케이스 B와 동일 규칙.** 화면에 없는 기호를 범례로 설명하지 않는다.

### 3-7. 색 배분 요약 (S-02 준수)

한 화면에서 채도 있는 색은 **정답 경로 하나**뿐이다.

```
무채색 (--ink 계열)  : 노드, 궤적, 엣지, 평면, 그리드, 모든 UI
--signal (바이올렛)  : 결정 깊이 선 + 그 위 마지막 토큰 노드 + 그 구간 궤적 + top-1 확률 막대
                       └ 이 넷은 "하나의 연속된 서사 객체"이므로 대상 1개로 센다
--seq-1~5           : Emb 층 놀람도 (바닥 한 줄에만)
--warn              : 경고 문구 텍스트·세로선 (면적 채움 금지)
```

**선택 강조는 시그널이 아니라 잉크(가장 진한 무채색)로 한다.** 선택은 UI 상태이고, 시그널은 데이터 서사다([2D스펙] P4).

## 4. three.js 구현 사양

### 4-1. 도입 (빌드 없음)

```html
<script type="importmap">
{
  "imports": {
    "three": "https://cdn.jsdelivr.net/npm/three@<VER>/build/three.module.js",
    "three/addons/": "https://cdn.jsdelivr.net/npm/three@<VER>/examples/jsm/"
  }
}
</script>
<script type="module" src="./js/3d/main.js"></script>
```

- `<VER>`는 **단계 1(기술 스파이크)에서 실제로 검증한 버전으로 고정**한다. `latest`·범위 지정 금지 — 발표 당일 CDN이 올린 새 버전에 깨지면 복구 불가.
- 오프라인 대비: 검증한 버전의 `three.module.js`와 사용한 addons를 `assets/vendor/three/`에 받아두고 importmap을 로컬 경로로 건다. 네트워크가 없어도 그대로 열린다.
- 사용 addons: `controls/OrbitControls.js`, `lines/LineSegments2.js`, `lines/LineSegmentsGeometry.js`, `lines/LineMaterial.js`.

**오프라인 번들의 함정 2개 (v1.4, 실측 확인)**

| # | 내용 |
|---|---|
| 1 | **r165+ 부터 빌드가 분리됐다.** `three.module.js`가 `./three.core.js`를 상대 경로로 import한다. 이 파일을 빠뜨리면 **CDN에서는 멀쩡하고 오프라인에서만 죽는다** |
| 2 | addons끼리 `three/addons/...` **bare specifier**로 서로를 참조한다. importmap에 `three` 매핑만 넣고 `three/addons/` 매핑을 빼면 역시 오프라인에서만 터진다 |

두 함정 모두 "파일을 받아뒀다"로는 안 잡힌다. §3-2의 실제 오프라인 부팅 검증이 유일한 확인 수단이다.

### 4-2. 렌더러 · 색 관리

```js
const renderer = new THREE.WebGLRenderer({
  antialias: true, alpha: false, powerPreference: 'high-performance'
});
renderer.setPixelRatio(Math.min(devicePixelRatio, 1.75));
renderer.setClearColor(cssColor('--paper'), 1);
// 색 관리: three r152+ 기본값(ColorManagement.enabled = true) 유지.
// CSS 변수는 sRGB 문자열이므로 반드시 setStyle(str, 'srgb')로 넣는다.
```

- **조명 없음.** `MeshBasicMaterial`만 쓴다. 이 화면은 물체가 아니라 도표다 — 음영은 값을 왜곡한다. 그림자·환경광·톤매핑 전부 끈다(`toneMapping = NoToneMapping`).
- `scene.background = cssColor('--paper')`. 안개(`Fog`)는 쓰지 않고 §3-2의 수동 색 혼합으로 대체한다(투명도와 안개가 겹치면 예측이 안 된다).

### 4-3. CSS 변수 → 머티리얼 (S-01)

```js
// js/3d/theme.js
const _cache = new Map();
export function cssColor(name) {
  if (!_cache.has(name)) {
    const v = getComputedStyle(document.documentElement).getPropertyValue(name).trim();
    _cache.set(name, new THREE.Color().setStyle(v, THREE.SRGBColorSpace));
  }
  return _cache.get(name).clone();
}
// 알파 대신 배경 혼합 (§4-5)
export function mixToPaper(c, alpha) { return c.clone().lerp(cssColor('--paper'), 1 - alpha); }
```

- 색 리터럴(`0x...`, `'#...'`)이 `js/3d/` 아래에 **1건이라도 있으면 반려.**
- 모션 시간도 동일하게 `--t-2`, `--t-3`, `--t-4`를 파싱해 ms로 쓴다.

### 4-4. 배치 구조 (draw call 최소화)

| 오브젝트 | 클래스 | 개수 |
|---|---|---|
| 노드 전체 | `InstancedMesh` 1개 + `instanceColor` | 1 |
| 세로 궤적 전체 | `LineSegments2` 1개 | 1 |
| attention 엣지(초점 층) | `LineSegments2` 1개 | 1 |
| sink 엣지 | `LineSegments2` 1개 (dashed) | 1 |
| 층 평면·결정선·그리드 | `Mesh`/`LineSegments` | 3~4 |

> **v1.4 정정.** 구 사양의 "총 draw call 8개 미만"은 근거 없는 숫자였다. 실측 내역은 노드 1 + 궤적 1 + 엣지 4(굵기 4단계) + 층평면 1 + 그리드 1 + 프레임 1 = **9개**이며, 전부 정당하다. **한 자릿수 draw call은 어느 GPU에서도 병목이 아니다** — 이 숫자를 지키려고 엣지 굵기 단계를 줄이는 것은 인코딩 품질을 공짜가 아닌 것과 맞바꾸는 손해다.

**숫자가 아니라 규칙으로 바꾼다.**

| 규칙 | 내용 |
|---|---|
| 단일 배치 (권장) | 노드·궤적·엣지는 각각 하나의 배치로 합치는 것을 기본으로 한다. **하드 규칙은 아니다**(§3-3 v1.5) |
| ~~머티리얼 공유가 본질~~ | **철회(v1.5).** 머티리얼을 96개로 나눠도 three.js가 캐시 키로 셰이더 프로그램을 공유한다 — 실측 확인 |
| 총 draw call | **≤ 12** 권장. 실측 9개(노드 1 + 궤적 1 + 엣지 4 + 평면 1 + 그리드 1 + 프레임 1)는 정상이다 |
| **진짜 예산은 프레임 시간** | draw call은 진단용 보조 지표다. 합격 판정은 §4-6의 fps·p99로 한다. 개발 머신에서 draw call 84 · 삼각형 11.8M에도 120fps였다 |

32B 최악에서도 GPU 부하는 사실상 노드 6,240 인스턴스 하나다. 01 문서가 우려한 73,000 엣지는 E-2 결정으로 **1,152개까지 줄었다.**

### 4-5. 굵은 선 — WebGL의 함정

**`LineBasicMaterial.linewidth`는 대부분의 WebGL 환경에서 무시되어 항상 1px로 나온다.** F-02(굵기 = 가중치)는 이 재질로는 불가능하다. 반드시 `LineSegments2` + `LineMaterial`을 쓴다.

```js
const mat = new LineMaterial({
  worldUnits: false,          // 화면 공간 px — 줌해도 굵기가 값 그대로 유지
  linewidth: 1,               // 실제 굵기는 인스턴스별로 못 준다 → 아래 참조
  vertexColors: true,
  dashed: false
});
mat.resolution.set(w, h);     // 리사이즈마다 갱신 필수. 빠뜨리면 굵기가 틀어진다
```

- **`LineMaterial`은 굵기를 세그먼트별로 줄 수 없다.** 해결: 굵기를 **4단계로 양자화**해 배치를 4개로 나눈다(`1.0 / 1.8 / 2.8 / 3.8 px`). 값의 연속성은 **투명도**가 담당하므로 정보 손실이 없고(이중 인코딩, S-03), draw call은 4개면 충분하다.
- **알파는 정점 색에 배경을 섞어 표현한다**(`mixToPaper`). `LineMaterial`의 정점 알파 지원이 버전마다 다르고, 반투명 선끼리의 정렬 문제도 피할 수 있다. 배경이 단색 `--paper`이므로 시각적으로 동일하다.
- 점선(sink)은 `dashed: true` + `computeLineDistances()` 필수. 빠뜨리면 실선으로 나온다.

### 4-6. 성능 예산 · 저사양 감축

| 항목 | 기준 |
|---|---|
| 회전 중 프레임률 | **60fps** (32B 최악) |
| 첫 렌더 | 분석 완료 후 **1초 이내** |
| 노드 인스턴스 갱신 | 층/토큰 선택 시 `instanceColor` 부분 갱신만. 지오메트리 재생성 금지 |
| 엣지 재빌드 | 초점 층 변경 시에만. 16ms 이내 |
| 자동 감축 | 최근 60프레임 평균 < 30fps면 ① pixelRatio 1.0 ② antialias off(컨텍스트 재생성) ③ 노드 세그먼트 16→8 ④ 궤적 보간 8→3분할 순으로 단계 적용, 감축 발생 시 상태 줄에 1줄 표시 |
| dispose | 재분석·모드 전환 시 `geometry.dispose()`·`material.dispose()`·`texture.dispose()` 전부. `renderer.info.memory`를 콘솔에 찍어 누수 감시 |
| **측정 방법 (v1.5)** | `avg fps`는 **vsync 상한에 묶인다**(120Hz 화면에서 항상 120). 여유를 알려면 **부하 사다리**로 잰다 — 노드·엣지 수를 2·4·8·16배로 올리며 무너지는 지점을 찾는다. `gl.finish()`는 Chrome/ANGLE에서 GPU 완료를 기다리지 않아 무의미하다(0.15ms 같은 값). **폐기된 지표이므로 하네스 출력에 남기지 않는다** |
| 측정 하네스 | `tools/perf_runner.mjs`. 가시성 가드 필수 — `document.visibilityState`와 워밍업 120프레임 중앙값으로 측정 불가 상태를 감지해 `valid: false` + `abortReason`을 반환하고 **측정을 시작하지 않는다.** hidden 탭에서는 `p99 = 1,532,272ms`나 `21,277fps` 같은 값이 나온다 — 둘 다 "빠르다"가 아니라 "안 돌았다"는 뜻이다 |
| 렌더 루프 | **상시 렌더 금지.** 카메라·선택·애니메이션이 변할 때만 `requestAnimationFrame` 1회(on-demand rendering). 정지 상태에서 GPU를 태우지 않는다 |

## 5. 카메라 · 컨트롤

### 5-1. 카메라

```js
const camera = new THREE.PerspectiveCamera(30, w / h, 0.1, 200);
```

- **FOV 30**. 넓은 화각은 원근 왜곡이 커져 "같은 크기 노드"가 다르게 보인다 — 도표에서는 왜곡이 곧 오독이다.
- `fitToBox(box, margin = 1.15)` — 씬 바운딩 박스가 화면에 들어오도록 거리 계산. 분석 완료·리사이즈·모드 복귀 시 호출.

### 5-2. 프리셋 3종 (F-05)

구면 좌표 `(azimuth, elevation, distance배율)` 로 정의. `distance`는 `fitToBox` 결과에 배율을 곱한다.

| 프리셋 | azimuth | elevation | 배율 | 성격 |
|---|---|---|---|---|
| **정면** | 0° | 0° | 1.00 | **2D 흐름도와 같은 구도.** 토큰×층 격자를 정면으로 읽는다 |
| **측면** | 90° | 0° | 1.05 | 의미 축(Z)이 가로로 펼쳐진다. 궤적의 좌우 흔들림 = 의미 이동 |
| **조감** | 28° | 62° | 1.20 | 층 평면들을 위에서. 토큰이 Z에서 모이는지 흩어지는지 |
| *(초기)* **3/4** | 32° | 18° | 1.00 | 한 프레임에 "3D임"과 "층 구조"를 동시에 전달 (D-7) |

- 전환: 위치·타깃을 **구면 좌표에서 보간**한다(직교 좌표 lerp는 씬을 관통한다). 시간 `--t-3`(420ms), 이징 `--e-inout`.
- 프리셋 버튼은 하단 컨트롤 바(§9-4). 활성 프리셋은 `--ink` 밑줄. 사용자가 수동 회전하면 활성 표시 해제.
- **정면 프리셋에서 직교 투영으로 전환**하면 2D와 완전히 같은 구도가 된다 — **P2**. 기본은 원근 유지.

### 5-3. 줌 · 스크롤 정책 (01 문서 D-4의 (ii) 채택)

**휠은 언제나 페이지 스크롤이다.** 3D 위에서 휠을 굴려도 씬은 줌되지 않는다.

| 조작 | 결과 |
|---|---|
| 좌클릭 드래그 | 회전 |
| Shift + 드래그 / 휠클릭 드래그 | 이동(팬) |
| 우클릭 드래그 (상하) | 줌 |
| 두 손가락 핀치 | 줌 |
| `+` / `-` 키 | 줌 (단계 8%) |
| 휠 | **페이지 스크롤** (씬에 전달 안 함) |

> **v1.1 수정.** 구 사양의 `controls.enableZoom = false`는 **휠뿐 아니라 우클릭 드래그와 두 손가락 핀치까지 전부 막는다** — OrbitControls에서 이 플래그는 dolly 경로 전체를 게이트하기 때문이다. 위 표(우클릭=줌, 핀치=줌)와 정면으로 모순이었다. 휠만 막으려면 **플래그가 아니라 이벤트를 가로채야 한다.**

```js
controls.enableZoom = true;                  // ← 켜둔다. 우클릭·핀치 줌이 여기 달려 있다
controls.enableDamping = true; controls.dampingFactor = 0.08;
controls.minPolarAngle = 0.15; controls.maxPolarAngle = Math.PI - 0.15;  // 뒤집힘 방지
controls.mouseButtons = {
  LEFT:   THREE.MOUSE.ROTATE,
  MIDDLE: THREE.MOUSE.PAN,
  RIGHT:  THREE.MOUSE.DOLLY
};

// 휠만 차단 — 캔버스의 "조상" 요소에서 캡처 단계로 잡아 OrbitControls보다 먼저 처리한다.
// 같은 요소에 캡처 리스너를 달면 등록 순서에 따라 순서가 뒤집힐 수 있으므로 반드시 조상에 단다.
stageEl.addEventListener('wheel', (e) => {
  if (e.target === canvas || canvas.contains(e.target)) {
    e.stopPropagation();      // OrbitControls에 도달시키지 않는다
    // preventDefault() 하지 않는다 → 페이지 기본 스크롤은 그대로 동작
  }
}, { capture: true, passive: true });
```

**터치 정책 (v1.1 재정의)**

OrbitControls는 연결 시 `domElement.style.touchAction = 'none'`을 강제하므로, 그대로 두면 **무대 위에서 세로 스와이프로 페이지를 스크롤할 수 없다.** sticky shrink(§5-4)와 정면 충돌한다.

```js
canvas.style.touchAction = 'pan-y';                        // 세로 스와이프 = 페이지 스크롤
controls.touches = { ONE: -1, TWO: THREE.TOUCH.DOLLY_ROTATE };  // 한 손가락 회전 비활성
```

| 입력 | 결과 |
|---|---|
| 한 손가락 드래그 | **페이지 스크롤** (씬 회전 아님) |
| 두 손가락 | 회전 + 핀치 줌 |

데스크톱 1024px 이상이 대상이므로(00 §8) 한 손가락 회전을 포기해도 손실이 작고, 스크롤을 잃는 쪽이 훨씬 치명적이다.

- 무대 우측 하단에 조작 힌트 1줄(`--t-cap`, `--ink-3`): `드래그로 회전 · Shift+드래그로 이동 · +/− 로 확대`. 최초 3회 방문까지만 표시 후 자동 숨김(localStorage).
- **검수 항목:** 휠로 페이지가 스크롤되는가 / 우클릭 드래그로 줌이 되는가 / 두 손가락 핀치로 줌이 되는가 — **셋을 각각 확인한다.** 하나만 보고 넘어가면 이 버그가 되돌아온다.

### 5-4. sticky shrink (E-3)

```
스크롤 0            무대 75vh, 히어로/컨트롤 전체 표시
스크롤 0 → 320px    무대 75vh → 36vh 선형 축소, position: sticky; top: 52px
스크롤 > 320px      무대 36vh 고정. 아래 밴드가 그 아래로 흐름
```

- 축소 중 `--t-*` 트랜지션을 쓰지 않는다. **스크롤 위치에 직접 연동**(`scroll` 이벤트 + `requestAnimationFrame` 스로틀)해야 손가락에 붙는다.
- 크기 변화마다 `renderer.setSize`, `camera.aspect`, `LineMaterial.resolution` 갱신. **셋 중 하나라도 빠뜨리면 선 굵기와 라벨 위치가 어긋난다.**
- 축소 상태에서는 `fitToBox`를 다시 호출해 씬이 잘리지 않게 한다. **단, 사용자가 수동으로 카메라를 움직인 뒤라면 호출하지 않는다**(`userAdjusted` 플래그). 남의 손을 밀치는 UI가 된다.
- 축소 상태에서 라벨 최대 개수를 24 → 10으로 줄인다(§6-2).
- `prefers-reduced-motion`에서도 sticky shrink는 유지한다 — 이것은 장식이 아니라 레이아웃이다.

## 6. DOM 라벨 오버레이 (F-06)

3D 공간에 텍스트를 렌더하지 않는다. 모든 글자는 캔버스 위에 절대 위치로 얹힌 DOM이다. 선명도·복사 가능·스크린리더·폰트 일관성 네 가지를 한 번에 얻는다.

### 6-1. 투영

```js
// 월드 좌표 → 화면 픽셀
const v = worldPos.clone().project(camera);
const sx = (v.x * 0.5 + 0.5) * rect.width;
const sy = (-v.y * 0.5 + 0.5) * rect.height;
const visible = v.z < 1 && sx > -40 && sx < rect.width + 40 && sy > -20 && sy < rect.height + 20;
el.style.transform = `translate3d(${sx}px, ${sy}px, 0)`;
```

- **`left/top`이 아니라 `transform`만 쓴다.** 레이아웃 재계산을 피한다.
- 변화량이 0.5px 미만이면 DOM 쓰기를 건너뛴다.
- 라벨 컨테이너에 `pointer-events: none`, 개별 라벨 중 클릭 대상만 `auto`.

### 6-2. 개수 · 우선순위

동시 표시 **최대 24개**(축소 상태 10개). 초과분은 우선순위가 낮은 것부터 숨긴다.

| 우선 | 라벨 |
|---|---|
| 1 | 선택된 노드의 상세 말풍선 |
| 2 | 결정 깊이 주석 |
| 3 | 초점 층의 토큰 라벨(T개) |
| 4 | 호버 중 attention 주석 |
| 5 | 층 눈금(Emb / 중간 / 최상단 3개만) |

- **카메라가 움직이는 동안에는 상한을 8개로 낮추고, 정지 후 120ms에 복원한다.** 회전 중 24개 DOM을 매 프레임 옮기면 저사양에서 눈에 띄게 끊긴다.
- 충돌 회피: 같은 축(세로)에서 18px 이내로 겹치면 우선순위가 낮은 쪽을 숨긴다. 밀어내지 않는다 — 라벨이 춤추면 더 산만하다.
- 오클루전: 초점 층이 아닌 층의 토큰 라벨은 애초에 그리지 않으므로 별도 depth 테스트가 필요 없다.

### 6-3. 라벨 스타일

- 토큰 라벨: `--t-num`, `--ink-2`, 배경 없음. 노드에서 `NODE_R` 만큼 위로 오프셋.
- 층 눈금: `--t-label`, `--ink-3`.
- 선택 말풍선: `--surface` 배경 + `--bd` + `--r-2` + `--shadow-pop`, 내부는 라벨/값/해석 3단([2D스펙] §4-7).
- **알약·뱃지 금지.** 배경 채움은 선택 말풍선 하나뿐.

### 6-4. 3D 안 주석 (P9 계승)

- 형태: 데이터 지점 → **무대 가장자리(±16px)** 까지 1px `--ink-4` 리더선(꺾임 1회, 화살촉 없음) + 텍스트 2줄 이내. 말풍선은 가장자리에 고정하고 **무대 안쪽으로** 자란다.
  - **v1.8 수정 (2026-08-27 디자인 감사).** 구 사양의 "12px 떨어진 곳"으로는 씬이 조밀할 때 말풍선이 여전히 점 구름 안이거나 토큰 라벨과 겹쳤다. 가장자리에 고정하고 리더선이 전 거리를 그어야 "가리키는" 관계가 성립한다. 결정 주석(상시 슬롯)은 자리가 매 프레임 옮겨 다니지 않도록 **항상 오른쪽**, 상태 연동 주석만 데이터 지점 쪽 가장자리를 따라간다. 두 주석이 같은 가장자리에서 44px 이내로 부딪히면 상태 연동 쪽을 밀어낸다.
  - ⚠️ **`<svg>` 오버레이에는 `width:100%; height:100%`를 명시해야 한다.** `<svg>`는 대체 요소(replaced element)라 `position:absolute; inset:0`만으로는 컨테이너를 채우지 않고 **고유 기본 크기 300×150으로 접힌다.** 실측에서 리더선 좌표가 전부 어긋나 "리더선이 없다"로 보였다.
- 상시 1개(결정 깊이) + 상태 연동 1개(호버/선택). **동시에 3개를 넘기지 않는다.**
- 리더선은 SVG 오버레이(`<svg>` 절대 위치, `pointer-events:none`)로 그린다. 캔버스에 그리면 라벨과 어긋난다.
- 주석 문장은 **[2D스펙] §5-2-1 sink 규칙**을 그대로 따른다. `sinkMass ≥ 0.5`면 sink를 설명하는 문장으로 대체한다.

## 7. 인터랙션 상태 머신

### 7-1. 상태

| 상태 | 진입 | 시각 변화 |
|---|---|---|
| `empty` | 분석 전 | 빈 격자 자전(§10-1) |
| `loading` | 분석 실행 | 자전 정지, 상태 줄 진행 바 |
| `idle` | 분석 완료 | 초점 층 = 결정 깊이(없으면 최상단). 주석 = 결정 깊이 문장 |
| `layer-focus` | 층 레일 클릭 / ↑↓ | 그 층 평면·노드·엣지 강조, 아래 밴드 1이 그 층으로 갱신 |
| `token-focus` | 토큰 노드 hover / ←→ | 그 토큰의 궤적만 진하게, 나머지 0.08. 주석 = 그 토큰의 attention 문장 |
| `node-select` | 노드 클릭 | `token-focus` 고정 + 선택 말풍선 + 아래 밴드 2가 그 토큰으로 갱신. 재클릭 해제 |
| `edge-hover` | 엣지 hover | 그 엣지만 `--ink`, 양 끝 토큰 라벨 강조, 주석에 가중치 표시 |
| `all-edges` | "전체 보기" 토글 | 전 층 엣지 표시(프루닝 상위 6). 라벨 전부 숨김. 성능 경고 1줄 |

- `layer-focus`와 `token-focus`는 **동시에 성립**한다(층 L18 + 토큰 "는").
- 모든 상태는 키보드로 도달 가능해야 한다(S-07). `↑↓` 층, `←→` 토큰, `Enter` 선택, `Esc` 해제, `1/2/3` 카메라 프리셋.

### 7-2. 피킹 (레이캐스트)

- `InstancedMesh`에 대한 `Raycaster.intersectObject`는 `instanceId`를 준다. 이걸로 `(layer, token)`을 역산.
- **매 mousemove마다 레이캐스트하지 않는다.** `pointermove`를 rAF로 스로틀하고, 이전 프레임과 포인터가 2px 이내면 건너뛴다.
- 히트 반경 보정: 노드가 작아 맞추기 어려우므로 `raycaster.params.Mesh.threshold`가 아니라 **화면 공간 최근접 탐색**으로 보완한다 — 투영된 노드 중심과 포인터 거리가 14px 이내인 것 중 카메라에 가장 가까운 것.
- 엣지 피킹은 `LineSegments2`의 `threshold`(px) 6으로.

### 7-3. 상태 ↔ 아래 밴드 연동 (C안의 핵심)

무대에서 무엇을 선택했는지가 **아래 섹션 제목에 즉시 반영**된다. 스크롤해서 내려갔을 때 "지금 무엇을 보고 있는지" 잃지 않게 한다.

| 밴드 | 제목이 반응하는 상태 |
|---|---|
| 밴드 1 | `layer-focus` → `L18 안에서 일어난 일` |
| 밴드 2 | `node-select` → `"는" — 이 토큰의 숫자` (선택 없으면 마지막 토큰) |
| 밴드 3 | 고정 (`진단`) |

- 상태가 바뀌면 아래 밴드 내용은 `--t-2` 크로스페이드로 교체. 스크롤 위치는 건드리지 않는다.

## 8. 모션

### 8-1. 등장 시퀀스 (F-08) — "데이터는 도착한다"

분석 완료 시 아래에서 위로 채워진다. 총 길이 약 1.6초.

| t (ms) | 동작 |
|---|---|
| 0 | 빈 격자 자전 정지, 카메라가 3/4 프리셋으로 이동(`--t-3`) |
| 0 – 900 | **노드가 아래층부터 순차 등장.** 층당 stagger = `min(24, 900 / L)` ms. 각 노드는 알파 0 → 목표, Y로 −0.3 → 0 |
| 300 – 1200 | 세로 궤적이 아래에서 위로 그려짐(`setLineDash` 진행 상당의 구간 렌더) |
| 700 – 1100 | 초점 층 평면 페이드 인, attention 엣지 좌→우 순차 드로잉 |
| 900 – 1400 | **결정 깊이 선이 그려지고, 그 위 마지막 토큰 노드가 `--signal`로 굳는다.** 이 구간이 화면의 클라이맥스이므로 다른 요소가 겹치지 않게 비워둔다 |
| 1100 – 1600 | 확률 막대 성장 + 수치 카운트업, 주석 텍스트 페이드 인 |

- 재분석 시에도 전체 재생. 층 변경 등 이후 갱신은 `--t-2` 크로스페이드만.
- **`prefers-reduced-motion`: 전 구간 생략하고 최종 프레임을 즉시 렌더.** 자전도 정지. `--t-*`를 0으로 만드는 것만으로는 rAF 루프가 멈추지 않으므로 **JS에서 명시 분기**한다(S-06).

### 8-2. 상시 모션

| 대상 | 규칙 |
|---|---|
| 빈 격자 자전 | 0.06 rad/s. 분석 시작 시 정지. reduced-motion에서 없음 |
| 자동 회전 | **없음.** 분석 후 씬은 사용자가 돌리기 전까지 정지한다. 자동 회전은 데모용으로만 `?autorotate=1` |
| 호버 반응 | `--t-1`(120ms) |
| 카메라 프리셋 | `--t-3` + `--e-inout` |

### 9-2. 상단 셸 (52px)

### 9-3. 층 레일 (무대 좌측, 떠 있음) — v1.1 재설계

> **구 사양의 버그.** 행 높이 `clamp(14, 420/L, 22)`는 `L=64`에서 14px × 65행 = **910px**이 되어 75vh 무대(≈675px)를 넘고 축소 상태(36vh≈320px)에서는 3배 초과였다. 축소 시 동작도 미정의였다. 아래로 교체한다.

**하나의 컴포넌트, 두 밀도 모드.** 사용 가능한 높이로 자동 전환한다.

```js
const availH = stageH * 0.70;                  // 무대 높이의 70%
const rowH   = Math.min(20, availH / (L + 1));
const mode   = rowH >= 16 ? 'rows' : 'axis';   // 16px 미만이면 글자가 안 들어간다
```

| 상태 | L | availH | rowH | 모드 |
|---|---|---|---|---|
| 무대 75vh (≈675px) | 24 | 472 | 18.9 | **행 목록** |
| 무대 75vh | 40 | 472 | 11.5 | **연속 축** |
| 무대 75vh | 64 | 472 | 7.3 | **연속 축** |
| 축소 36vh (≈320px) | 24 | 224 | 9.0 | **연속 축** |

→ **축소 상태에서는 층 수와 무관하게 연속 축이 된다.** 이것이 구 사양의 미정의 구간에 대한 답이다.

#### 9-3-1. 행 목록 모드 (L ≤ 약 28, 무대 확대 시)

**[2D스펙] §4-4 그대로.** 폭 104px. 층 이름(mono) + 미니 바(그 층 top-1 확률) + 결정 깊이 `◆`.

> **v1.8 수정 (2026-08-27 디자인 감사).** **`Emb`(l=0)는 미니 바·스파크라인에서 제외한다. 축 눈금 라벨은 남긴다.** Emb의 `top1_prob`은 (대개 묶인) 임베딩 가중치를 통한 자기유사성 때문에 **항상 ≈1.0**이다 — 로짓 렌즈의 알려진 특성이지 데이터 오류가 아니다. 그대로 그리면 Emb가 매번 "가장 확신에 찬 층"처럼 보이고, 실제 층들과 같은 척도에 얹힌 인공적 최댓값이 스파이크로 찍힌다.
>
> ⚠️ **행 모드 컨테이너에 `display:flex`를 무조건 걸지 말 것** — `[hidden]`의 `display:none`과 명시도가 같아 **`hidden` 속성을 이긴다.** 축 모드로 전환해도 이전에 그려둔 행이 유령처럼 남는다(실측: 32B 축 모드에서 "Emb 라벨이 축에서 붕 떠 있는" 현상의 정체). `:not([hidden])`으로 명시도를 올린다.
초점 층은 배경 `--ink` / 글자 `--paper`.

#### 9-3-2. 연속 축 모드 (신설)

층 65개를 65줄로 쓰지 않는다. **축 하나 + 스파크라인 하나**로 바꾼다 — 정보량은 늘고 공간은 준다.

```

┌──────────────┐

├──────────────┤
│ L63 ┤  ╲      │   ┤ = 5의 배수 눈금 (1px --line-strong)
│     ┤   ╲     │   곡선 = 층별 top-1 확률 스파크라인
```

| 축 | 세로 1px `--line-strong`. **결정 깊이 위 구간만 `--signal`** (3D의 "굳는" 은유를 레일에서 반복) |
| 눈금 | 5의 배수 층에 가로 4px 선. `L ≥ 48`이면 10의 배수 |

| 스파크라인 | 층별 top-1 확률(마지막 토큰 위치)을 잇는 폴리라인 1개, `--ink-4` 1px. **65개 막대보다 "언제 확신이 생기는지"가 곡선 모양으로 훨씬 잘 읽힌다** |

- **백엔드에 `lens[l].top1_prob`가 필요하다**([2D스펙] R-30과 동일). 없으면 스파크라인 없이 축만 렌더 + 콘솔 경고.
- 키보드: `↑↓` 1층, `PageUp/PageDown` 5층, `Home/End` 처음·끝. 두 모드 동일.
- 모드 전환은 `ResizeObserver`로 감지하고 **크로스페이드 없이 즉시 교체**한다(스크롤 중 깜빡임 방지).

## 11. 데이터 계약 (백엔드)

3D가 요구하는 것은 **기존 응답의 작은 확장 3개**뿐이다.

| ID | 필드 | 형태 | 공수 | 비고 |
|---|---|---|---|---|
| **B-01** | `hidden_proj.pc1` | `float[L+1][T]` | **0.1일** | 기존 q=2 결과의 1축. **q=3 확장 불필요**(§2-3) |
| **B-01b** | 시점 정렬 적용 | — | **0.2일** | `_hidden_projection`을 `logit_lens.proj()`와 **코드 경로 공유**로 변경 (§2-3-1) |
| **B-01c** | `pca_lowrank` 시드 + `niter≥12` | — | **0.1일** | 결정론 확보. **2D 경로에도 동일 적용** (§2-3-1) |
| **B-01d** | `hidden_proj.evr` · `overflow` · **`squashed`** | `float` | 포함 | 캡션 상시 표기 + **런타임 가드**(§2-3-2 v1.6) |
| **B-02** | `hidden_proj.pc1_scale` | `float` | 포함 | 95퍼센타일 절대값 |
| **B-03** | `hidden_proj.sign_fixed` | `bool` | 포함 | 부호 고정 적용 여부 |
| **B-04** | `lens[l].top1_prob` | `float` | 0.2일 | 층 레일 미니 바(§9-3) |
| **B-05** | `attention.pruned` | `{k: 12, dropped: int, threshold: 0.02}` | 0.3일 | 생략량 로그(D-02) |
| **B-06** | `subsample` | `{stride: int, shown: int, total: int} \| null` | 0.3일 | 층 서브샘플링 표시(D-03) |

- 페이로드 상한 **1.5MB** 유지. 초과 시 층 stride를 2 → 4 → 8로 올린다.
- **attention은 초점 층 요청 시에만 전송**해도 된다(E-2). 초기 응답에 전 층 attention을 넣지 말고 `/api/attention?layer=L` 지연 로드로 바꾸면 32B 응답이 4.5MB → 100KB대로 떨어진다. **권장이며, 공수 0.3일.**
- 응답 스키마 변경 시 2D 폴백도 같은 응답을 쓰므로 **필드 추가만 하고 기존 필드를 바꾸지 않는다.**

### 12-1. `이 화면 읽는 법` 본문

> 가로는 문장의 토큰 순서, 세로는 층입니다. 맨 아래가 방금 넣은 문장이고, 위로 갈수록 모델이 계산을 거듭한 상태입니다.
> 앞뒤 방향은 **의미**입니다. 같은 토큰이라도 층이 올라가면서 앞뒤로 움직이는데, 그게 "문맥을 반영해 의미가 바뀌는" 모습입니다.
> 앞뒤 축은 수백 개 숫자를 한 줄로 눌러 담은 것이라 전체의 일부만 담습니다. 가까이 있으면 의미가 비슷하다고 보는 근사입니다.
> 세로로 이어진 선 하나가 토큰 하나의 여정이고, 보라색으로 굳는 높이가 **답이 정해진 층**입니다.
> 가로로 걸친 곡선은 그 층에서 어떤 토큰이 어떤 토큰을 봤는지(attention)입니다. 선택한 층에만 그려집니다.

### 15-4. 최종 판정 — "예쁘지만 의미 없는 3D"를 피했는가

01 문서가 지목한 최대 위험에 대한 판정 기준. 단계 5 게이트와 단계 7 종료 시 각각 확인한다.

1. 화면을 **10초 보고** "어느 층에서 답이 정해졌는지" 말할 수 있는가?
2. 3D를 정면으로 돌려놓으면 2D 흐름도와 같은 정보가 읽히는가? (연속성)
3. **회전시켰을 때 새로 알게 되는 사실이 있는가?** — 없으면 3D일 이유가 없다. 있어야 할 답: "층이 올라갈수록 토큰이 앞뒤로 흩어진다/모인다"
4. 색을 다 빼도(그레이스케일) 결정 깊이가 보이는가? (기준선 = 형태 인코딩)
5. 모델을 0.5B → 32B로 바꿨을 때 **실루엣이 눈에 띄게 다른가?** — 근거는 셋이며, ②가 가장 크다:
   ① 총 높이 비 1.00 : 1.63(§2-2) ② **결정 깊이의 상대 위치** ③ 층별 의미 축 퍼짐 패턴.
   높이 하나만으로 판정하지 않는다 — 높이 차이는 층 수를 세면 알 수 있는 정보라 그 자체로는 가치가 없다.
6. 화면에 "이 그림이 말하는 한 문장"이 실제로 적혀 있는가?
